# S2 2.1 Constraint- Project Scope

## Learning Objectives

Define the project term triple constraint.

First, what is a project scope? The project scope (or scope statement or statement of scope) is, simply put, what the result of the project is desired to be. It defines the product of the project. It is sometimes referred to as the statement of work (SOW). A scope statement includes the following:

- project objectives
- project deliverables
- product acceptance criteria
- technical requirements
- project limits and exclusions
- project milestones
- project constraints
- project assumptions

A well-written scope will clearly define every aspect of the project, including functions and features, quality expectations, and time constraints. There will be no ambiguity and nothing left to interpretation. This is extremely important in helping avoid scope creep.

This depicts scope creep with a three-headed creature saying “Let’s add this feature!” “That’ll cost ya!”, and “We need another week!” Scope creep must be avoided. This issue is dangerous to the health of the project. Scope creep occurs when there are any—but particularly small or incremental—additions to the project scope that are not subject to the formal scope change process. This occurs because the scope was not well written due to oversights or limited understanding. As you move through the project, you get more knowledgeable and your understanding gets better, and often you learn things you did not know at the start. Ambiguities in the initial information or new information can lead to scope creep. Any items that are not clearly and completely defined can lead to scope creep. Over time, if the project scope escalates and work is being performed that was not originally budgeted, it puts a strain on all project resources and can cause the project to run over budget, behind schedule, or have lower quality.

Instead of allowing scope creep, iterative planning is sometimes used. Like scope creep, it can be dangerous and costly but often necessary if your understanding changes. The more you work on a project, the more you can see changes. It is recommended to keep a list of those changes or use change control techniques and save the list of changes for another project or time. The most critical objective of doing projects is to deliver something of value in a timely manner and at a reasonable cost. If you continually stop and start with changes, you will never deliver useful functionality to the client, and resources and time will be wasted.
